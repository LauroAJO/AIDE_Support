================================
AIDE — RELATÓRIO v2.25.8
DEX Staging: curadoria antes de importar
================================
Data: 2026-08-02

CONTEXTO:
O sync do DEX (v2.25.7) importava contatos direto em network_people.
Esta versão introduz uma waiting room (dex_contact_staging) igual ao
padrão já usado pela bridge do Lifegame (bridge_person_staging): contatos
do DEX ficam pendentes de revisão em /dex/staging antes de virar registro
em network_people.

MUDANÇAS:
- migrations/0047_dex_staging.sql (nova)
  - CREATE TABLE dex_contact_staging (id, dex_contact_id UNIQUE, full_name,
    first_name, last_name, email, phone, job_title, company, description,
    linkedin, image_url, raw_payload, staged_at, reviewed, approved,
    rejected, imported_person_id FK → network_people ON DELETE SET NULL,
    imported_at)
  - idx_dex_staging_reviewed, idx_dex_staging_dex_id
  - Aplicada localmente (npm run db:migrate) — OK

- _worker.js
  - Rota dispatch (bloco DEX CRM): + GET /api/dex/staging,
    GET /api/dex/staging/count, POST /api/dex/staging/approve,
    POST /api/dex/staging/reject, DELETE /api/dex/staging/clear
  - syncDexContacts() reescrita: em vez de INSERT/UPDATE em network_people,
    faz INSERT ... ON CONFLICT(dex_contact_id) DO UPDATE em
    dex_contact_staging. Por contato do DEX:
      1. já tem pessoa em network_people (por dex_contact_id OU email)
         → already_imported++, pula
      2. já está em staging → upsert (atualiza com dado mais recente do
         DEX, preserva reviewed/approved/rejected/imported_person_id —
         não usei INSERT OR REPLACE puro pra não resetar o status de
         revisão de quem ainda está pendente)
      3. novo → INSERT em staging, staged++
      4. sem nome (full_name vazio após join first+last) → skipped++
    Retorno: { fetched, staged, skipped, already_imported } (troquei
    { total, inserted, updated, skipped } do v2.25.7)
  - handleDexStagingList/Count/Approve/Reject/Clear (novo bloco, logo
    após handleDexSync) — mesmo padrão de handleBridgePeopleStaging*
  - handleDexStagingApprove: por id, resolve pessoa existente (por
    dex_contact_id OU email) e só vincula; senão cria em network_people
    com source='dex', tags='[]'

- src/components/networking/DexStagingPage.jsx (nova)

ROTAS ADICIONADAS:

POST   /api/dex/staging/reject   → owner only, { ids: [...] } → { rejected }
DELETE /api/dex/staging/clear    → owner only, → { deleted }
