INCIDENTE ENCONTRADO E CORRIGIDO DURANTE O DEPLOY (importante):
Depois do primeiro deploy, fiz QA manual no navegador (login já ativo
do usuário) e encontrei DOIS bugs reais, não pegos por build/node --check:

1) Migração 0048 nunca tinha sido aplicada no D1 remoto → TODO PUT
   /api/network/people/:id (edição de qualquer pessoa, não só peso
   setorial) passou a retornar 500 "no such column: sector_weight" em
   produção, porque a query UPDATE referencia as colunas novas
   incondicionalmente. Ou seja, o deploy quebrou a edição de contatos
   no Networking até a correção.
   → Pedi confirmação ao usuário (ação em banco remoto/produção) e,
   aprovado, rodei:
   npx wrangler d1 execute aide-db --remote --file=migrations/0048_sector_weight.sql -y
   Aplicada com sucesso (6 queries, 121 rows written).

2) Mesmo com a migração aplicada, salvar "Peso Setorial" ainda derrubava
   a página inteira (ErrorBoundary "Algo deu errado"). Decodifiquei o
   stack minificado com sourcemap (source-map package já em
   node_modules) e localizei: NetworkingPage.jsx, useMemo `allTags`
   (`people.forEach(...)`). Causa raiz: `setPeople` é o setter do
   Zustand (`setNetworkPeople: (networkPeople) => set({ networkPeople })`),
   que NÃO aceita updater funcional como o `useState` do React. Minha
   função `patchPerson` chamava `setPeople((list) => list.map(...))` —
   isso atribuía a PRÓPRIA FUNÇÃO como valor de `networkPeople` no
   store, e o próximo `people.forEach` quebrava com "a.forEach is not
   a function".
   → Fix: `patchPerson` passou a calcular o array primeiro
   (`setPeople(people.map(...))`, usando o `people` já em escopo) em
   vez de passar uma função para o setter. Rebuild + redeploy
   (https://49b003ec.aide-support.pages.dev) + reverificado no
   navegador: salvar peso setorial funciona sem erro, em Lista, Tabela,
   Heatmap e Mapa.
   Dado de teste usado durante a verificação (Alessio Trivella,
   sector_weight=5, notas="teste") foi revertido para null via API
   depois do teste — não ficou lixo em produção.
